### 1.2 Runtime topology (as configured in code)

- **Web:** Daphne single process (`Dockerfile:39`, `docker-compose.yml:38-41`), ASGI app = Django HTTP + Channels websocket (`Config/asgi.py:20-27`). Startup command runs `migrate` and `collectstatic` on every container start (`docker-compose.yml:38-41`).
- **Workers:** one `celery worker` container (`docker-compose.yml:70`, default prefork concurrency = CPU count = 4), one `celery beat` container (`:97`).
- **Data:** Postgres 16 (`:2-18`), Redis 7 (`:20-32`) as Celery broker + result backend + Channels layer (`Config/settings/celery.py:18-39`). **Django cache = LocMemCache** unless `USE_REDIS_CACHE=True` (`base.py:161-177`); the brief's `.env` key list does not contain `USE_REDIS_CACHE`, so production runs the per-process in-memory cache.
- **Edge:** nginx → `127.0.0.1:8000` (`deploy/nginx-myclosly.conf:17`), `/media/` served from disk with `expires 7d` and `Access-Control-Allow-Origin *` (`:9-13`), 25 MB body limit (`:6`), 120 s proxy timeouts (`:31-33`).
- **Static:** WhiteNoise (`base.py:89`, `:251-258`).

## 2. How it works — end-to-end flows

### 2.1 HTTP request lifecycle (any API call)
1. nginx receives TLS (live) / port 80 (repo conf `nginx-myclosly.conf:1-2`), sets `Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto` (`:25-28`); it does **not** set or strip `X-Forwarded-Host`, so a client-supplied one passes through.
2. Daphne accepts; Django's ASGI handler runs the sync view in a per-request `ThreadSensitiveContext` thread (Django 5.2 behaviour for sync views under ASGI).
3. Middleware order (`base.py:86-98`): CORS → Security → WhiteNoise → Session → Common → CSRF → Auth → **`TranslationMiddleware`** → **`UserActivityMiddleware`** → Messages → XFrame.
4. DRF authenticates via JWT or Firebase (`drf_swagger.py:9-12`); throttles anon/user (`:13-25`).
5. View returns `standard_response(...)` (`users/views/base.py:7-32`) or a hand-built dict; errors funnel through `Config.exceptions.custom_exception_handler` (`drf_swagger.py:8`).
6. On the way out, `UserActivityMiddleware` writes two LocMem cache keys per authenticated request (`users/middleware.py:112-120`, `users/utils/user_activity.py:7-13`).
7. If `user.preferred_language` is not `en`, `TranslationMiddleware` parses the JSON body, walks every string value and, for each not in `SKIP_KEYS`, calls `GoogleTranslator(...).translate(data)` synchronously (`users/middleware.py:33-53,75-102`); results cached 24 h in LocMem (`:93-98`).

### 2.2 Container boot / deploy
1. Operator runs `git pull` + `docker compose up --build` (brief). Three services each `build: .` the same Dockerfile (`docker-compose.yml:35,67,94`) → the image is built three times.
2. Dockerfile copies the tree and chowns to `appuser` (`Dockerfile:30-33`), but compose bind-mounts `.:/app` and `./media:/app/media` (`docker-compose.yml:44-46,73-75,100-101`), so the image content is shadowed by the host checkout (including `.env`, `.git`, the Firebase service-account JSON and `celerybeat-schedule`).
3. `web` waits for db/redis health (`:60-64`) then runs `migrate --noinput && collectstatic --noinput && daphne …` (`:38-41`). `celery_worker` and `celery_beat` only wait for db/redis (`:87-91,113-117`), not for `migrate` → they can start executing tasks against a half-migrated schema during a deploy that adds columns.
4. No healthcheck on `web`, `celery_worker`, `celery_beat`; `restart: unless-stopped` only restarts on process exit, not on hang.
5. Port `8000:8000` is published on all host interfaces (`:47-48`); only the Hetzner cloud firewall (22/80/443) prevents direct plain-HTTP access to Daphne (brief: ufw inactive).

### 2.3 AI garment scan (the one LLM path) — synchronous
1. `POST /api/closet/ai-scan/` (`closet/urls.py:29`; alias `clothes/ai-scan/` `:24`) → `ClosetAIScanView.post` (`closet/views/scanner_views.py:55`), throttle 15/min/user (`:52`).
2. `validate_image_file(image_file, max_mb=30)` — extension + size only, no magic bytes, no EXIF strip (`users/validators.py:175-206`).
3. `closet.views.scan_clothing_image(...)` (`scanner_views.py:76-77`) → **saves the raw upload to `media/closet_items/` first** (`closet/ai_scanner/scanner.py:35-36`) → `analyze_dress_with_openai` (`:43-45`).
4. `run_direct_dress_analysis` (`closet/openai_analyzer.py:131-222`): SHA-256 LocMem cache (`:153-159`, TTL 600 s) → `ai_service.validate_image_size` rejects **> 5 MB** (`dress-analyzer-ai/config.py:10`, `service.py:73-76`) → acquires a process-wide `BoundedSemaphore(15)` with 35 s timeout (`:12-15,165-168`) → **synchronous OpenAI GPT-4o vision call** (`:175` → `service.py:79-99`) → optional **Apify Google search** for brand (`:191-193` → `service.py:135-193`, code comment `:197` cites "20s cloud scraper") → Pydantic validation.
5. Any exception (including the 5 MB `ValueError`, a HEIC that OpenAI rejects, a network error) is swallowed in `analyze_dress_with_openai` (`openai_analyzer.py:331-333`) and returns `None`; `scan_clothing_image` then tries Gemini (key unset, `scanner.py:59-63`) and finally the **"built-in heuristics engine"** (`:65-70`) or a hard-coded default dict (`:71-93`, name "Classic Wardrobe Essential", price 35.00). The `visual_match_score` is clamped to 88–98 whatever the source (`:100-105`).
6. Response 200 with pre-fill data; with `?auto_save=true` a `ClosetItem` is created and points awarded (`scanner_views.py:106-192`).

### 2.4 Celery beat schedules
`expire_old_stories_task` hourly (`social/tasks.py:8-18`, single `UPDATE`), `sync_awin_feeds_task` / `sync_rakuten_feeds_task` every 5 h (`affiliate/tasks.py:8-36`, each wraps `call_command`, swallows exceptions and returns a string), `cleanup_old_notifications_task` daily (`notifications/tasks.py:9-19`). AWIN sync: bulk upsert with `update_conflicts` (`sync_awin_feeds.py:185-195`), timestamp-based deactivation only after a full parse (`:283-292`), 30-day purge (`:306-315`). No task locks, no retries, no time limits.

### 2.5 GDPR deletion via web (no login) — the risky path
1. Anyone POSTs `name`+`email` to `/api/users/delete-account-request/` (`gdpr_views.py:119-152`, `csrf_exempt`, `AllowAny`).
2. A `verification_link` is built with `request.build_absolute_uri(...)` (`:136-138`) → host taken from `X-Forwarded-Host` because `USE_X_FORWARDED_HOST=True` (`base.py:289`) and `ALLOWED_HOSTS` contains `"*"` (`base.py:31`).
3. Email sent from the developer's Gmail (brief) with the link.
4. **`GET /api/users/verify-account-deletion/<token>/` performs `user.delete()` immediately** (`gdpr_views.py:164-176`), no login, no confirmation POST.
5. Media files of the deleted user are not removed (Django does not delete `ImageField` files on row delete; grep finds no `post_delete`/storage delete except the profile picture in `common_utils.py:166-170`).

### 2.6 Admin purge
Unfold admin (`unfold.py`), public `/admin/` (`Config/urls.py:38`). The changelist and change form render an `<a href>` to `admin:accept_account_deletion` (`users/admin.py:147-152`; `templates/admin/users/accountdeletionrequest/change_form.html:630`); `process_single_approval` (`users/admin.py:197-209`) accepts **GET** and calls `purge_and_anonymize_user` with no `request.method` check.

### 2.7 Media
Every uploaded photo (closet items, outfits, stories, DM images, profile pictures) gets a uuid filename (`users/models.py:9-12`, `scanner.py:35`) under `media/` and is served by nginx to anyone holding the URL (`nginx-myclosly.conf:9-13`) and, as a second path, by Django's `static.serve` in production (`Config/urls.py:51-56`). URLs are embedded in API responses (`users/fields.py:9-20`, `users/utils/media_utils.py:33-79`).

## 3. Strengths — what is done well

- **Settings are modular and env-driven** (`Config/settings/__init__.py`, `python-decouple` throughout `base.py`); Docker DB-host detection (`base.py:128-139`) makes the same image work on host and in compose.
- **Every view sets `permission_classes` explicitly** (grep §1.5 + 56 `IsAuthenticated` sites) even though the DRF default is unsafe; JWT auth is the default class (`drf_swagger.py:9-12`).
- **Auth hardening details:** OTP generated with `secrets` (`users/utils/common_utils.py:7-11`), constant-time compare (`users/views/auth_views.py:460`), OTP expiry auto-clear (`users/models.py:230-255`), dedicated throttles per IP+email for OTP/reset (`users/throttling.py:30-93`), login throttle (`:66-76`), refresh-of-deleted-user → 401 not 500 (`auth_views.py:575-581`, tested `users/tests.py:264-280`).
- **Uniform JSON error envelope** guaranteed by `Config/exceptions.py:13-99` (no HTML 500s), and unhandled exceptions are logged with tracebacks (`:49-50`).
- **Money-adjacent code uses row locks**: `select_for_update()` inside `transaction.atomic()` for point awards and expiry (`rewards/services.py:95-99,166-168`).
- **Catalog sync is idempotent and safe on partial failure**: `bulk_create(update_conflicts=True, unique_fields=['aw_product_id'])` (`sync_awin_feeds.py:185-195`), deactivation keyed on `updated_at < sync_time` and only after a complete parse (`:283-292`), 30-day purge instead of immediate delete.
- **Containers run as a non-root user** (`Dockerfile:25-33`); Postgres/Redis bound to `127.0.0.1` (`docker-compose.yml:11,25`); db/redis have healthchecks and `web` waits for them (`:14-18,28-32,60-64`).
- **Uploads:** uuid filenames everywhere; chat images are re-encoded through Pillow (drops EXIF, caps 1280 px) (`users/utils/media_utils.py:82-143`); size validation (`users/validators.py:175-206`).
- **AI scan has real back-pressure controls** exposed as env (`base.py:306-308`): concurrency semaphore, queue timeout → 503 with `Retry-After` (`scanner_views.py:78-84`), SHA-256 result cache (`openai_analyzer.py:153-159`).
- **Tests exist and cover authorization edges** (69 tests): private outfit hidden from others (`social/tests.py:353-389`), non-author PATCH → 403/404 (`:407-439`), other user's notification not deletable (`notifications/tests.py:93-97`), PII fields excluded from user sub-objects (`social/tests.py:549-605`), throttle 429 (`users/tests.py:318-331`), self-like/self-view suppression, image size/format validation.
- **Health endpoint** checks DB and Redis with latency (`Config/views.py:88-156`); OpenAPI schema is tagged and documented (`drf_swagger.py:121-178`).

## 6. Can it work for the app? — verdict for this area

The platform layer is a competently assembled, conventional Django/DRF/Celery stack: settings are modular and env-driven, containers run as non-root, Postgres and Redis are bound to localhost, throttles and constant-time OTP checks exist, catalog sync is idempotent, and there is a 69-test suite that exercises many authorization edges. For an invite-only TestFlight with ~150 users the raw capacity is not the problem: one Daphne process on a 4-vCPU VM will serve this cohort's API traffic with headroom (§10).

What is not acceptable for real users, even at 150, is the security and operations baseline. Three items are blockers in the literal sense: (1) the combination of a wildcard `ALLOWED_HOSTS`, `USE_X_FORWARDED_HOST=True` and unauthenticated GET endpoints that hard-delete accounts gives an outsider a low-effort account-deletion attack; (2) there is no database backup of any kind; (3) the JWT signing key may be the committed insecure default (unverified — the `.env` inventory does not list `SECRET_KEY`). Each of these is a one-day fix. Just behind them: CORS reflects any origin with credentials, the admin is public with no 2FA or rate limit and a GET-triggered purge, cookies and HSTS are unset, access tokens live seven days, and Firebase tokens with user PII are written to unrotated logs.

Against the specification the gap is structural rather than incremental. The spec's platform chapter assumes a worker-isolated photo pipeline (NSFW gate → EU LLM → cost log → kill switch), private storage with signed URLs, structured logs, Sentry, CI gates and a config surface. None of that exists; the one LLM path runs synchronously in the web process against OpenAI (US) and silently falls back to fabricated results when anything fails, photos are world-readable by URL, and the only observability is a health endpoint nobody polls. Of the 25 acceptance items, none is fully met and 19 are not met. The i18n approach (runtime Google-Translate scraping of every response for Hindi/Portuguese users; no German at all) shows the codebase was not built for the DACH product described in the spec — as does the "Closly" branding, the `closly://` scheme and a users app whose first migration predates the engagement by eight months.

Can it work? As a beta backend after the S-effort security/ops fixes in P-01…P-03, P-06…P-10, P-16 and a log/CORS/host cleanup: yes, for 150 invited users who accept English UI text. For the November public launch it needs the M-effort items: asynchronous fit checks with a real failure mode, private media, a config/kill-switch layer, CI + Sentry + backups + pinned dependencies, one canonical API surface, and German strings. The good news is that most of this is additive on top of what exists rather than a rewrite; the exception is the AI scan pipeline, which should be rebuilt as a worker job before it carries the product's core loop.

## 7. Recommended alternative / target design (incremental)

**Week 0 (before any real user) — all S:**
1. `ALLOWED_HOSTS` from env only, delete the hard-coded list and `"*"`; `USE_X_FORWARDED_HOST=False`; nginx `proxy_set_header X-Forwarded-Host ""`. Deletion/profile-wipe verification: GET renders a confirm page, POST executes, and executes a *soft* delete that enqueues the purge. (`base.py`, `gdpr_views.py`)
2. Verify/rotate `SECRET_KEY`; remove the default; `DEBUG` default `False`.
3. Nightly `pg_dump | gpg | rclone` to an EU object store + one tested restore; document in `ops/BACKUP.md`.
4. `CORS_ALLOW_ALL_ORIGINS=False`; HSTS, secure cookies, `SECURE_SSL_REDIRECT`; commit the real nginx TLS config with `limit_req` zones for `/admin/login/` and `/api/users/*`; admin behind IP allow-list; purge action `require_POST`.
5. SimpleJWT: access 30 min, refresh 30 d, `BLACKLIST_AFTER_ROTATION=True`.
6. Remove the three token/header log lines; JSON log formatter; docker log rotation; `chmod 600 .env`.
7. Delete `TranslationMiddleware` + `deep-translator`; `preferred_language` choices `de/en`.
8. `DEFAULT_PERMISSION_CLASSES=[IsAuthenticated]`; affiliate routes authenticated; docs behind `IsAdminUser`; remove Django's prod `/media/` route.
9. Pin dependencies (lockfile), digest-pin the base image; GitLab CI with `test` (Postgres service), `makemigrations --check`, `pip-audit`; Sentry EU DSN; UptimeRobot on `/api/health/ping/`.

**Before public launch — M each:**
10. **Async fit check:** `POST /api/closet/ai-scan/` → validate (magic bytes, ≤5 MB, JPEG/PNG, EXIF strip via Pillow re-encode) → store to a private `media/private/` prefix → create `ScanJob(status=queued)` → Celery task (`acks_late`, `time_limit=120`, `autoretry_for=(APIError,)`, max 3) → LLM through one `closet/ai/llm.py` wrapper that writes an `LlmCostLog` row (model, tokens, cents, user) and checks a daily cap → status `done|failed|budget` → client polls `GET /ai-scan/{id}/`. No heuristics fallback; failed = failed. Same wrapper honours `MYC_AI_KILLSWITCH`.
11. **Private media:** nginx `location /media/private/ { internal; }` + a JWT-checked Django view issuing `X-Accel-Redirect` (or `django-storages` + S3-compatible EU bucket with signed URLs); `post_delete` cleanup + weekly orphan sweep; purge files in the GDPR cascade.

**Later (post-launch):** PgBouncer or `CONN_MAX_AGE=0`; Redis cache (`USE_REDIS_CACHE=True`) before a second web process; Telegram cost/sync digests; DSA report endpoint; export job.

## 10. Capacity estimate (no load test exists; figures are engineering estimates from the code and the VM spec)

**Topology facts:** one Daphne process (single Python interpreter, GIL) on CPX32 (4 vCPU, 8 GB shared with Postgres, Redis, a 4-process Celery worker and beat). Sync Django views run in one thread per in-flight request (unbounded thread count). Postgres `max_connections` default 100. AI scans: process-wide semaphore 15, queue timeout 35 s, nginx read timeout 120 s, per-user throttle 15/min.

| Workload | Estimated ceiling of the current single process | What limits it |
|---|---|---|
| Light authenticated JSON endpoints (profile, notifications, closet list; ~2–5 queries, ~15–40 ms) | ≈ 30–80 req/s sustained; p95 < 200 ms up to ≈ 20 req/s | GIL (≈1 core effective), `UserActivityMiddleware` 2 cache writes/request |
| `for-you` feed (dozens of `ILIKE` OR-conditions with `Case/When` scoring over the 7k-row products table, no trigram/GIN index; Python-side variant dedupe) | ≈ 5–15 req/s before Postgres CPU saturates (unverified) | Sequential scans; grows linearly with catalog size (a 50k-SKU catalog would drop this to ~1–2 req/s) |
| Websocket chat | thousands of idle sockets fine; per-message DB write + group send | Redis channel layer; 120 s nginx idle timeout requires client pings (consumer supports `ping`, `consumers.py:63-64`) |
| **AI scan** (5–30 s OpenAI + 0–20 s Apify) | hard cap **15 concurrent**; throughput ≈ 15 ÷ mean latency ≈ **1–2 scans/s theoretical, ~1/s realistic**; the 16th–Nth requests wait ≤35 s then 503 | Semaphore; each in-flight/waiting scan holds one thread, one Postgres connection (`CONN_MAX_AGE=600`) and 2–3× the image size in RAM (bytes + base64 + PIL) |

**150 Early-Access users** (≈30–50 DAU, evening peak ≈10 concurrent, a few scans/minute): comfortably within limits; p95 latencies dominated by the LLM call itself. Nothing breaks on capacity grounds; the risks at this stage are the security/ops findings, not load.

**5,000 users** (≈1,500 DAU, evening peak ≈150 concurrently active, ≈20–40 light req/s, scans bursting to 20–100/min after a push notification or launch post):
1. **First to break: a scan burst.** 100 users scanning within a minute → 15 run, 85 threads block on the semaphore for up to 35 s, each holding a DB connection → with the worker's 4 and beat's 1, Postgres hits 100 connections → *every* endpoint returns 500 ("too many connections", mapped to 400 by the handler) until the waiters time out. Memory: 100 × ~10–30 MB ≈ 1–3 GB transient, plausible OOM on an 8 GB box that also runs Postgres.
2. **Second: nginx 120 s timeout vs. LLM+Apify worst case** (35 s wait + 30 s LLM + 20 s Apify = 85 s, but retries/slow Apify runs exceed 120 s) → client sees 504 while the server still pays for the call and saves the image.
3. **Third: feed CPU** at 20–40 req/s of `for-you` on an unindexed 7k+ table shared with Postgres on the same 4 vCPU → p95 in the seconds; the GIL-bound Daphne process cannot be scaled horizontally without first moving throttles/online-status/scan cache from LocMem to Redis (`USE_REDIS_CACHE`) and making beat a singleton.
4. **Fourth: disk** from unrotated INFO logs (full headers per Firebase login) and never-deleted media.

**Headroom after the recommended changes:** scans in Celery (worker concurrency 4–8, `time_limit`) remove the thread/connection coupling entirely — the web tier then handles ≈50–100 req/s of light traffic per process, and 2–3 Uvicorn/Gunicorn workers behind nginx (Daphne kept only for `/ws/`) put 5,000 MAU on the same VM with Postgres as the next bottleneck (add a trigram index on `name`/`brand`/`category` or precompute feed pages per spec C3).
